# TT 用户 Prompt 指南（TT-USER-PROMPT-GUIDE）

> 面向：用 TT 工作流驱动项目的负责人/产品 owner。
> 目的：在项目各阶段用 Prompt 发挥 TT 工作流的 100% 能力——**用 Prompt 触发 gate，把决策权留在该留的地方，让纪律替你管 LLM**。
> 适用：TT 2.9+（含契约冻结 / HTML 双 gate / 竞品批判 / 前置条件 / 棕地契约 / 独立实证验收）。

---

## 0. 核心心智模型

```
你的 Prompt = 定边界 + 触发 gate + 只保留你独有的决策权
LLM 能力发挥 = gate 逼出来的（验收不采信报告、批判必对标、契约先冻结、前置不满足不开工）
```

TT 把**纪律**做成了机器可校验的硬约束（契约 hash、`DEP_PRECONDITION`、`review-gate`、URL 真验、`--verify-urls`），但把**方向、审美、取舍**留给你。Prompt 的价值不是"指挥它做事"，而是**在每个 gate 前做出该由人做的决策**：

| 人工 gate | 你该做的 | 敷衍后果 |
|---|---|---|
| 概念版签收 | 明确说"确认"才推进 | 方向错，后面 gate 全为错误方向把关 |
| 前提挑战（Step0） | 逐条确认前提 | 方向对错失守 |
| 契约审阅 | 用业务场景审接口/错误码 | 契约冻结了错误接口 |
| HTML APPROVED（Gate A） | 审美签收才准写框架 | 返工成本高一个量级 |

纪律再硬，拦不住"人没定方向"。

---

## 1. 阶段 0：立项 — 一句话定边界

```text
用 TT 工作流做「<项目一句话>」。约束我替你定死：
- 先走需求挖掘 gate（§2.1），逐轮问我 ≤2 题，我确认一个你才推进
- 全程遵守：契约先冻结、HTML 原型要我 APPROVED、每轮验收强制竞品对标批判
- 技术栈我倾向 <A>，但若你调研后认为 <B> 明显更优，给出竞品证据反驳我
- 本阶段只做需求澄清 + 概念版，不拆任务不写代码
```

为什么有效：`只做第 N 步` 激活 TT 的"可回跳"模型；`允许反驳` 打开批判 gate；`契约/APPROVED/批判` 三词是 TT 纪律的钥匙——不写这些，TT 只是普通问答。

**反例**：
> "帮我做个学习平台，要 AI 个性化，前端要好看"

会跳过需求 gate 直接按它的想象拆任务。

---

## 2. 阶段 1：需求挖掘 — 你当唯一事实源

```text
先别产文档。按 forcing-questions 逐轮问我（每次 ≤2 题）：
1. 这解决谁的真问题？现在怎么解决、差在哪？
2. 最强的 1-2 个同类是什么？我和它的核心差异？
3. 最难的技术点、最小可交付版是什么？
竞品数据/市场规模/技术选型一律回源核验，查不到标[待补充]不许编。
概念版产出后我先签收（明确说"确认"）才进下一步。
```

TT 的 §2.1 gate 会"追问直到挖干净"——你只回答，它负责结构化。查不到的标 `[待补充]`，禁止编造（防幻觉红线）。

---

## 3. 阶段 2：拆任务 — 前提挑战是唯一必须你拍板的点

```text
拆任务前先走 dev-planner Step0 前提挑战：产出 ≤6 条前提 + 4 问结论
（为什么现在/现状方案/窄楔子/未来适配），逐条给我确认。
前提通过后：每个 task 带 GWT 验收 + 前后置依赖 + 契约冻结顺序 + 选型依据。
前端页面每页一个 task，走 HTML 原型 gate。
拆完跑 review-gate --plan 自检三视角（CEO/Eng/Design）。
```

关键：前提挑战是**方向正确性**的最后一次人工把关。你确认前提，错的是方向；任务怎么拆，错的是可改细节。

---

## 4. 阶段 3：契约冻结 — 你业务知识最值钱的地方

```text
后端契约冻结前，把接口清单/schema/错误码/响应壳列出来，
我用真实业务场景逐条审（这是我最该把关的），审完才冻结。
冻结后执行期禁止改契约；要改走变更单 + 重验收。
前端任务开工前必须已有冻结契约，缺契约就停下告诉我，不要臆造接口。
```

### 棕地（老系统无 OpenAPI）补充

```text
若后端是老系统无 OpenAPI，用棕地模式：
contract-reverse 反推草案 → 后端确认 → 冻结；
前端可凭草案先开工（--contract-draft），接口变更走 discrepancy 变更单上浮。
```

---

## 5. 阶段 4：派单执行 — 最短但最不可妥协

```text
按 C-01 派独立子 agent 执行（task/claude/codex/openclaw），你不得自写自验。
每任务完工 = 你独立实证验收（跑测试/真实请求/git log），不采信完工报告。
验收通过才解锁下游。前端：HTML 原型先我 APPROVED（Gate A）才准写框架。
每个验收断言逐个复现给我看，不要只说"通过了"。
```

90% 的翻车发生在验收偷懒——只信报告、或验收只走形式。这条让"独立实证"成为默认动作而非可选项。

---

## 6. 阶段 5：验收批判 — 喂毒，方向感是你给的

```text
每轮验收后强制技术批判：真实搜索竞品对标（GitHub stars/官方文档/近1-2年
benchmark），URL 可达性机器验证（--verify-urls），不足 3 条有效批判按硬闸门拒绝。
批判要毒舌，拿同类顶级项目挑刺，不许客气。
每条批判登记 tracker，生成后续任务待优化项；下一轮派单开工前核对承接。
```

你补方向感：

```text
重点批判我选的库/架构是否过时？有没有现成开源方案我在重复造轮子？
我的方案在真实负载/生产环境哪里会崩？和<竞品X>比差的本质是什么？
```

---

## 7. 阶段 6：改需求 / 迭代 — 只说 delta

```text
用户改了需求：<delta，具体到行为和边界>。
按 TT 回跳规则只重跑影响层：文档→重拆→重规划→看板，已实施产物不回退。
此变更影响哪些已冻结契约？列变更单，下游等重验收再解锁。
```

**反例**："重新做一遍吧"——会回退到阶段 0 或全量重拆，浪费已实施产物。你的 Prompt 要明确**哪一层**。

---

## 8. 阶段 7：怀疑结果 / 防幻觉 — 打假 Prompt

```text
我不信这个结论。用独立复现/真实数据证给我看：
- 每个数字/URL/结论标证据来源（回源核验）
- 禁止引用你自己或上一步产出的文档作为证据（防自证）
- 查不到的标 [待补充]，禁止编造
```

---

## 9. 一张表总结

| 阶段 | 你该写的核心 | 你独有的决策 |
|---|---|---|
| 立项 | 做 X + 定死纪律 + 只做第 1 步 | 边界/范围 |
| 挖掘 | 追问我，我确认一个推一步 | 方向/概念签收 |
| 拆任务 | 先前提挑战给我确认 | 前提（方向对错） |
| 契约 | 接口清单我审完再冻结 | 业务契约正确性 |
| 派单 | 独立子 agent + 独立实证验收 | 验收口径 |
| 验收 | 真实竞品对标批判 + 登记 backlog | 批判方向感 |
| 改需求 | 只跑影响层 + 变更单 | 变更影响面 |
| 打假 | 独立复现 + 禁自证 | — |

## 10. 贯穿性技巧

| 场景 | 你该写的 |
|---|---|
| 首次跑大项目 | 开头加："全程按 TT 8 步闭环，每步产物落盘后我确认再继续" |
| 改需求 | "用户改了需求：<delta>。按影响面只重跑对应层，已实施产物别回退" |
| 发现它绕 gate | "你刚才跳过了 HTML 原型审核/契约冻结，回退到该 gate 重走" |
| 质疑结果 | "我不信这个结论，用独立复现/真实搜索证给我看，禁止引用你自己产出的文档" |
| scope 失控 | "只做 <task 清单>，越界的一律不碰；需要改别人模块先写 discrepancy 上浮" |
| LLM 幻觉防范 | "产出的每个数字/URL/结论标证据来源；查不到的标 [待补充]，禁止编造" |
| 前端任务 | "HTML 原型要我先 APPROVED（Gate A）才准写框架代码" |
