## C1 · --update 内联防跳校验（P0）

**修改**（`yy/scripts/tt-journey.mjs`）：
1. `updateJourney()` 在 L118 `node.status='done'` 前插入：`const chk = prereqCheck(journey, n); if (!chk.ok && !opts.force) throw new PrereqError(chk.reason)`（新导出错误类，携带 exit code 3）。
2. `main()` 的 `--update` 分支捕获 PrereqError → stderr 输出原因 + 「--force 可越过」，exit 3。
3. 新增 `--force` flag：越过时 stderr 打 `WARN: prereq bypassed by --force`，并在 journey.json `plans[]` 追加 `{planId:'__manual__', status:'prereq-bypassed', updatedAt}`（留痕不吞）。
4. `orchestrator.mjs syncJourney()`（L171）写前同样调 `prereqCheck`（step8 依赖 step7；失败仅 warning 不阻断——派生是事实记录，非状态推进）。
5. `validate-structure.mjs` 增规则：commands/*.md 正文必须包含 `--prereq-check` 调用行字样（当前 grep 证实 0 文件含此行）。

**量化指标**：未满足前置时非法更新成功率 100%→0%；`--force` 留痕率 100%。
**测试方案**：新增 GWT6（step5 未 done + `--update --step 7` → exit 3、journey.json 字节不变）；GWT7（同场景 + `--force` → exit 0、plans[] 含 prereq-bypassed 记录）；回归 `regression-all.mjs` 8/8。
**风险**：棕地场景 journey 不存在时 `--update --step 0` 应放行（PREREQ_MAP 无 0 项，天然放行，无破坏）；orchestrator 失败路径派生若被误阻断会丢失败记录——故第 4 点只 warning。

## C2 · 并发写保护（P0）

**修改**：自研最小锁（零依赖，符合 yy 零运行时依赖纪律；不引 proper-lockfile 以免 9 依赖树膨胀）：
1. `tt-journey.mjs` 新增 `withJourneyLock(file, fn)`：`open(lockPath, 'wx')`（O_EXCL）→ 执行 fn → unlink；lockPath = `<journey>.lock`。
2. 获取失败重试 5 次 × 400ms；仍失败 → stderr `WARN: journey lock busy, proceeding without lock`（可用性优先，记录告警）。
3. `updateJourney` 与 orchestrator `syncJourney` 均经 `withJourneyLock` 包裹。
4. 死锁自愈：lock 文件 mtime > 30s 视为 stale，直接接管。

**量化指标**：20 轮 2 进程并发 `syncJourney`（不同 planId）→ plans[] 双条目存活率 100%；锁等待 P99 < 2s。
**测试方案**：新增 `integration-e2e.mjs` 场景（或独立 `test-concurrent-journey.mjs`）：spawn 2 子进程同时收尾 × 20 轮，断言最终 JSON 含两个 planId；`--self-test` 增 GWT8（进程内模拟读-改-写窗口交错，验证锁生效）。
**风险**：lock 文件残留（进程被 kill）→ stale 检测兜底；Windows `wx` flag 行为已验证支持 O_EXCL 语义。

## C3 · Windows GBK 渲染降级（P1）

**修改**（`tt-journey.mjs renderJourney`）：
1. 新增 `renderAsciiMode()` 判定：`process.platform==='win32'` 且非 `WT_SESSION`/`TERM=xterm-256color` 时启用 ASCII 降级（或 CLI 显式 `--ascii` 强制）。
2. ASCII 模式：`done=[x]`、`in_progress=[·]`、`pending=[ ]`；节点名用 STEPS 定义新增 `en` 字段（如 `asset-init`/`doc`/`split`/`plan-contract`/`dispatch`/`feedback`）。
3. 中文说明行（当前位置/下一阶段）在 ASCII 模式换英文（`NOW:`/`NEXT:`/`GATE:`）。

**量化指标**：chcp 936 下输出以 GBK 解码 100% 无替换字符（乱码字节 0）。
**测试方案**：新增 GWT9：`process.env.FORCE_ASCII=1`（测试钩子）→ 渲染输出不含 ✓/●/○ 与中文字符；真机冒烟：cmd chcp 936 + 重定向文件 GBK 解码 clean。
**风险**：低；纯渲染层，schema 不动。

## C4 · 位置判定只认正向主干（P1）

**修改**（`currentAndNext`，tt-journey.mjs:172-190）：
1. `current`/`next` 判定范围改为 FORWARD_LINE（`steps.filter(s=>FORWARD_LINE.includes(s.step))` 内取 in_progress 或首个非 done）。
2. 渲染主干行后追加回跳层一行：`~ 2/4/6 回跳层：按需（done 视为该层历史完成）`。
3. 全主干 done 时输出「当前位置：全部主干节点已完成（回跳层按需）」，不再报「下一阶段：无」死路文案。

**量化指标**：E6 场景（0/1/3/5/7/8 done、2/4/6 pending）→ 「当前位置」正确指向主干结论，回跳层仅附注。
**测试方案**：GWT10：steps 0/1/3/5/7/8 done、2/4/6 pending → 断言输出含「全部主干节点已完成」且不含「重执行1（待推进）」；既有 GWT1 不回归。
**风险**：低；GWT1 断言需同步微调（其用例 5 in_progress 不受影响）。
