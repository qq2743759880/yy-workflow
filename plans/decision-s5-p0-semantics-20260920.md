# 裁决：S5 P0 未清零口径（⬜ vs ⬜◐）— 2026-09-20

裁决人：编排者（Owner 2026-09-20 授权）。状态：**已裁决，待按实施项落地**。

## 背景

同一份 tracker，两处"open P0"口径不一致：
- `scripts/ci.mjs` S5 硬闸门：`| P0 |` 且含 `⬜` → 阻塞（**◐ 不算**）
- `scripts/orchestrator.mjs` `backlogIsPending`：`⬜` 或 `◐` → pending（**◐ 也算**）

## 选择 1：维持 ci ⬜-only（登记分歧）— 5 条连锁遗留

1. **矛盾工件**：同一 tracker 下 ci 报 PASS、orchestrator READY 计算报 pending——R6 验收包
   与第三方复现会拿到互相矛盾的结论，证据链出现裂缝（与项目"证据链闭环"的核心价值冲突）。
2. **永久◐漏洞**：P0 修一半弃坑，行永远停在 ◐——严格语义下是未清零，此口径下永远绿灯，
   发布可能带病出航且事后无法从记录区分"修完"与"弃坑"。
3. **分歧固化进 lib**：lib/ci.mjs 已忠实抽取 ⬜-only；B0 翻默认后宽松语义被三处工件固化，
   日后修正的成本与波及面只会更大。
4. **对外解释成本**：R6 第三方证据以 CI PASS 为核心；按行业常理"open P0"含 in-progress，
   每次对外都要加口径脚注，且容易被判定为证据不实。
5. **先例效应**：保留分歧 = 默认"两个口径都合法"，后续新增 gate 复制哪个口径变成抛硬币，
   分歧自身成为新的遗留问题发生器。

## 选择 2：直接统一 ⬜◐（硬切）— 5 条连锁遗留

1. **误伤进行中工作**：若 CI 在工作中间被跑，进行中的 P0 让 S5 常红——CI 从就绪信号退化
   成常态红灯（缓解：CI 本就只在验收/发布检查点跑，需把该纪律成文化）。
2. **历史证据语义漂移**：M1-M3 与 R6 的 12/12 PASS 取得于 ⬜-only 口径——新口径下不可复现，
   无 grandfathering 声明则验收链自相矛盾。
3. **违反自家变更纪律**：S5 行为被多份验收报告引用过，改语义不走 change.record（C-R7）
   就是"冻结后改行为不走出兵"的自我打脸。
4. **◐ 自报可信度**：◐ 由 agent 自报，严格口径让闸门依赖自报状态——可能被用于 progress
   theater（把永不修完标 ◐ 观望，或把该 ⬜ 的标 ◐ 绕其他检查）。
5. **测试资产波及面**：lib/ci countOpenP0、GATE_TOPOLOGY 断言、A1 的 22 项探针、B0 双跑
   fixture、T2 验收记录——五处需同步更新，漏一处即产生"探针新口径、实现旧口径"的静默分叉。

## 裁决：选择 2 的方向 + 选择 1 的问题清单作为实施约束（综合案）

**统一严格口径：`⬜` 与 `◐` 都算未清零。** 理由（对应工作流自己的三红线）：
- "独立实证验收，不采信报告"——进行中的修复**没有完成证据**，P0 就是未清零；
- S5 与 backlogIsPending 都是 go/no-go 闸门（检查点跑，非持续灯），go/no-go 时刻的
  in-progress = no-go；
- S5 立项动机（6e5fe06/f42cb16："P0 修复前 M3 不得开始"）的"open"本就应含 in-progress。

### 实施项（走 change.record，编排者派 T7）

1. `OPEN_P0_PATTERN` 常量化（lib/ci.mjs 单点定义，ci.mjs 与 orchestrator 共同引用）——
   杜绝第三次分叉（消解选择 1-#3/选择 2-#5）。
2. change.record 登记（语义变更非缺陷修复）+ **grandfathering 声明**：历史 ACCEPTED 报告
   按取得时口径有效（消解 2-#2/2-#3）。
3. **◐ 证据卫生规则**：gate 时 ◐ 行必须携带落点任务/收据引用，无引用按 ⬜ 处理
   （消解 2-#4，兼收 1-#2）。
4. CI 检查点纪律成文（CI 在验收/发布检查点运行，非持续灯）（消解 2-#1）。
5. 同步更新：lib 差分 fixture + A1 探针期望 + B0 双跑基准（消解 2-#5）。
