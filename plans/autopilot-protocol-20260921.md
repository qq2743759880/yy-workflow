# 自动驾驶管线协议 autopilot v1（2026-09-21）

目标：单会话内，编排者（本会话）驱动**单个执行者子代理**（独立上下文）连续自动执行
约 20 个 task，Owner 零中继。三条不可破纪律映射到机制，不是口号。

## 一、角色与铁律（纪律 → 机制）

| 纪律 | 机制（怎么保证，不是"要求保证"） |
|---|---|
| C-01 执行≠验收 | 执行者=后台子代理（独立上下文，无本会话历史）；验收=编排者亲自：范围核对（git diff 波基线 tag）→ 复跑执行者自测 → **完工后才编写**的盲测探针（≥3 条反走捷径假设）→ P0/P1/P2 分级 |
| 盲测纪律 | ① 验收探针写在 `test-reports/acceptance-*/`，执行者派单明令禁读（8 批实战无违例）；② 探针在执行者完工后编写（时序保证）；③ **盲行者 agent 特殊规则：一次性运行，永不向它发返工单**（返工会暴露它被测的事实）——坑修复派给另一个工匠 agent |
| 批判纪律 | 每份验收报告强制登记发现（分级）+ 残留问题；波门跑全量回归 12/12；每 5 个 task 一次管线自批判（本文件 §六的清单逐条复检） |
| 队列更新 | 看板/队列文件是唯一事实源：`plans/autopilot-queue-20260921.md`（管线队列）+ `plans/blindwalk-board-20260920.md`（盲行坑登记）。执行者**禁写**这两个文件（不在其白名单）；编排者在每个波门更新 |

## 二、核心循环（波次制）

```
┌─ 波开始（编排者）──────────────────────────────┐
│ 1. git tag auto-w<N>-base（波基线，验收范围核对锚）│
│ 2. 写/补该波各 task 的派单 brief（handoffs/）      │
│ 3. 后台启动执行者 agent（单agent串行做该波2-3个task）│
│    batch brief：逐task读brief→施工(白名单内)→     │
│    自测→写REPORT→下一个；禁读acceptance/*/；      │
│    禁git；禁写队列/看板                           │
└──────────────────────────────────────────────┘
          │ agent 完成通知到达（无需 Owner）
          ▼
┌─ 波门（编排者，每task独立验收）──────────────────┐
│ 4. 范围核对：git diff auto-w<N>-base vs 白名单    │
│ 5. 复跑执行者自测 + 盲测探针（完工后新写）          │
│ 6. 分级：ACCEPTED→逐task独立commit；REWORK→       │
│    SendMessage 唤醒同一agent发返工单（≤2次，       │
│    超限标记blocked跳过，管线继续）；盲行者task除外  │
│ 7. 更新队列/看板 + 日志 checkpoint                │
│ 8. 回归全量 12/12 门 → 下一波                     │
└──────────────────────────────────────────────┘
```

"不中断"的确切含义：**Owner 零参与**（通知驱动，我在同一会话自动接力），不是无门控直通——
波间门控是"不把后浪建在前浪的沙子上"的必要代价（批判#1 如实声明）。

## 三、状态与断点续跑（抗死亡设计）

- **日志** `plans/autopilot-journal.md`（append-only）：每波记录 agentId、基线 tag、
  每 task 验收判定、待办动态槽内容。**我的上下文被压缩后靠它恢复**，不靠聊天记忆。
- **执行者死亡**（配额/超时——本项目历史上真实发生过）：从队列文件重建剩余 task，
  新起 agent 带剩余 brief 继续（工匠 agent 无状态可重建；盲行者 agent 死了就重跑一次，
  它本来就该一次性）。
- **基线 tag**：波前打 tag，验收范围核对与部分产出的清理（git checkout 未授权文件）都锚它。

## 四、盲行者任务的特殊管线（BW-*）

1. **全新 agent + 只有盲行 Prompt**（身份不可泄露：无本会话历史、无 handoffs 可见性、
   prompt 措辞已审定——见 blindwalk 协议 §2.2）
2. 它的工作区 `D:\.ai-hub\tmp\project-run-*`；验收=读它的 session-notes + workspace
   取证 + 日志/db 复现，** grading 对象是"坑的质量"不是"项目做没做完"**
3. 坑 → 登记看板 → 修复 task 进动态槽 → 派给**工匠 agent**（绝不回发给盲行者）
4. 盲行会消耗真实 token/时间：每波只跑 1 个 BW task

## 五、队列（20 task 蓝图，详见 queue 文件）

W1-W2 修复批（FIX-1 workspace 坑 / FIX-2 executor 接线 / FIX-3 断言解耦 / FIX-4/5 T9 残留）
→ W3 加固化批（junction 冒烟入回归 / 发布目录一键脚本 / purge 纪律）→ W4 BW-1 盲行 →
W5 动态修复槽(×2-4) → W6-W8 BW-2/3/4 → W9 动态修复槽 → W10 终验+收口报告。
动态槽在波门由编排者按盲行发现填写——**20 是容量设计不是凑数承诺**（发现少则槽坍缩）。

## 六、管线自批判 10 条（每 5 task 复检）

1. 波间门控 vs "不中断"的矛盾已声明：每波门约 10-30 分钟编排者验收，管线停但人不参与
2. 执行者跨 task 上下文累积（一个 agent 做 2-3 个 task ≈ 100-300 次工具调用）——
   超限风险靠波次小型化 + 无状态重启兜底；**验收探针保密目前是文件级约定而非强制**
   （更强隔离=执行者在独立 git worktree 施工，合并回主树——留作升级项未启用）
3. 盲行者=我的子代理、同模型：独立上下文成立，但行为多样性弱于外部平台（盲区可能同源）
4. 我的验收探针跨波趋同（我自己写自己的考题）——缓解：每波强制 ≥1 个全新类型断言
5. 配额死亡是历史事实（9-20 五小时上限打断过 T1/T2）——日志+队列已可断点续跑，
   但跨配额周期需要 Owner 说"继续"
6. 20 commit 的历史粒度：逐 task 独立 commit 便于回滚，但 rebase/整理成本留给收口批
7. 动态槽 brief 由波门时的我编写——若我上下文恰在压缩边界，journal 是唯一安全网
8. BW 盲行会话无法预知时长（上一次烧了 24 分钟+配额）——波内只放 1 个 BW + 超时止损
9. 执行者自测 PASS 无证据效力（只供自纠）——已有机制，重申防滑坡
10. 管线本身无人验收（我是最后一环）——Owner 抽查点：每波门后可看板复核；
    W10 收口报告给 Owner 全量复核机会

## 七、启动与终止

- 启动词：Owner 说"开工"→ W1
- 终止：队列清空 / Owner 说"停" / 不可恢复死亡（记 journal 后停）
- 每波门后我在会话里输出一行进度（`[autopilot] W<N> done: x/y accepted, z rework, n blocked`）
