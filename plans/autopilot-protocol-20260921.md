# 自动驾驶管线协议 autopilot v1（2026-09-21）

目标：单会话内，编排者（本会话）驱动**单个执行者子代理**（独立上下文）连续自动执行
约 20 个 task，Owner 零中继。三条不可破纪律映射到机制，不是口号。

## 一、角色与铁律（v2：纪律 → 机制）

| 纪律 | 机制 |
|---|---|
| C-01（有人值守派发） | 原样保留：编排者亲自盲测验收 |
| **C-01-B（无人值守口径，Owner 2026-09-21 裁定）** | ① 复核者 = 异上下文**重执行**（命令级原始输出留痕，不采信结论）——C-01 反信任本质保住；② 复核者只出临时判定，完工判定权在编排者收口；③ 收口三重义务：审计 100% 复核 raw 日志（不读结论摘要）+ 亲自全量复验全部 RED 级/触契约任务 + 随机 ≥3 采样复验 + 其余凭日志抽查放行 |

## 二、五层流水线与单任务 8 步循环（v2 核心）

### 五层

- L0 批次组装（编排者，人工门前）→ **唯一一次 Owner 确认**
- L1 执行单元：每 task 派**全新独立上下文执行者**（现有 dispatch 纪律不变）
- L2 独立复核单元：每 task 派**另一个全新上下文复核者**，重执行全部证据
- L3 登记单元：轻量登记员 agent（或脚本）——台账追加，不动冻结件
- L4 批次收口：编排者裁定、落盘修订、队列正式更新

### 单任务 8 步

1. 开工双检：冻结件 SHA256 比对 + tar 备份（备份落 test-reports/autopilot-snapshots/）
2. 执行（白名单纪律照旧）
3. 执行者交付「**证据已交付**」（不自称 DONE）
4. 独立复核：复核者**自己算哈希、自己重跑全部探针/E2E/回归门、审计写面
   newer-than-dispatch 文件清单、GWT 逐条、discrepancy 完备性**——命令级原始输出留痕
   （复核日志 test-reports/autopilot-reviews/<task>/）
5. 结构化判定：PASS / FAIL / RED_LINE（复核者只出临时判定，完工判定权在编排者收口）
6. 修复环：同执行者 ≤2 轮返工 → 仍败则换新执行者 + 续跑简报 → 仍败则任务隔离、
   下游自动 BLOCKED、队列继续
7. 台账登记（L3）：batch-ledger.md 追加（任务/判定/证据指针/耗时），不改冻结件
8. 盲测队列增量评估：本 task 是否改变盲测就绪态（BT-02/GT-01/PROD-01 快照）——
   正式更新在收口；盲测目录对全部角色只读

### 严格串行与确定性驱动

- 任务 k 复核完成前 k+1 不开工（防 8101/5173 端口冲突与写面竞态——沿用既有教训）
- 驱动环 = 编排者会话内的确定性主循环：读队列文件 → 派 L1 → 等通知 → 派 L2 →
  收判定 → L3 → 下一个。状态全在队列/台账/journal 文件，编排者上下文压缩后可无损重建
- "不中断"边界：RED_LINE 立即全批停（冻结哈希漂移 / 写面外写入 / 探针基线回归 /
  复核环境中毒信号）；看门狗：执行 90min / 复核 60min 超时 → 杀 → 续跑简报换上下文
  （网关击杀类死亡同走此路，不算中断）

## 三、状态与断点续跑（抗死亡设计）

- **日志** `plans/autopilot-journal.md`（append-only）：每波记录 agentId、基线 tag、
  每 task 验收判定、待办动态槽内容。**我的上下文被压缩后靠它恢复**，不靠聊天记忆。
- **执行者死亡**（配额/超时——本项目历史上真实发生过）：从队列文件重建剩余 task，
  新起 agent 带剩余 brief 继续（工匠 agent 无状态可重建；盲行者 agent 死了就重跑一次，
  它本来就该一次性）。
- **基线 tag**：波前打 tag，验收范围核对与部分产出的清理（git checkout 未授权文件）都锚它。

## 四、盲行者任务的特殊管线（BW-*）

1. **全新 agent + 只有盲行 Prompt**（身份不可泄露：无本会话历史、无 handoffs 可见性、
   prompt 措辞已审定——见 blindwalk 协议 §2.2）
2. 它的工作区 `D:\.ai-hub\tmp\project-run-*`；验收=读它的 session-notes + workspace
   取证 + 日志/db 复现，** grading 对象是"坑的质量"不是"项目做没做完"**
3. 坑 → 登记看板 → 修复 task 进动态槽 → 派给**工匠 agent**（绝不回发给盲行者）
4. 盲行会消耗真实 token/时间：每波只跑 1 个 BW task

5. 复核环境中毒 → RED_LINE 信号之一（复核者发现环境异常即停批）

## 六、管线自批判 10 条（每 5 task 复检）

1. 波间门控 vs "不中断"的矛盾已声明：每波门约 10-30 分钟编排者验收，管线停但人不参与
2. 执行者跨 task 上下文累积（一个 agent 做 2-3 个 task ≈ 100-300 次工具调用）——
   超限风险靠波次小型化 + 无状态重启兜底；**验收探针保密目前是文件级约定而非强制**
   （更强隔离=执行者在独立 git worktree 施工，合并回主树——留作升级项未启用）
3. 盲行者=我的子代理、同模型：独立上下文成立，但行为多样性弱于外部平台（盲区可能同源）
4. 我的验收探针跨波趋同（我自己写自己的考题）——缓解：每波强制 ≥1 个全新类型断言
5. 配额死亡是历史事实（9-20 五小时上限打断过 T1/T2）——日志+队列已可断点续跑，
   但跨配额周期需要 Owner 说"继续"
6. 20 commit 的历史粒度：逐 task 独立 commit 便于回滚，但 rebase/整理成本留给收口批
7. 动态槽 brief 由波门时的我编写——若我上下文恰在压缩边界，journal 是唯一安全网
8. BW 盲行会话无法预知时长（上一次烧了 24 分钟+配额）——波内只放 1 个 BW + 超时止损
9. 执行者自测 PASS 无证据效力（只供自纠）——已有机制，重申防滑坡
10. 管线本身无人验收（我是最后一环）——Owner 抽查点：每波门后可看板复核；
    W10 收口报告给 Owner 全量复核机会

## 七、启动与终止

- 启动词：Owner 说"开工"→ W1
- 终止：队列清空 / Owner 说"停" / 不可恢复死亡（记 journal 后停）
- 每波门后我在会话里输出一行进度（`[autopilot] W<N> done: x/y accepted, z rework, n blocked`）


## 八、并行修订（Owner 2026-09-22 指令："能并行就并行"）

严格串行的**原语义保留于同写面任务**（竞态教训），修订为**写面正交即可并行**：

- 并行判定器（编排者波门执行）：两个 task 的 L1 写面白名单交集为空 → 可并行
- 并行上限：同时 ≤3 个 L1 在途（子代理并发）；L2 复核随各自 task 完成即派（不排队）
- 写面分区：
  - 区 A = webview/journey/**（FE-4 专属）
  - 区 B = scripts/** 产品脚本（FIX-1/FIX-2/FIX-3 互斥同区 → 仍串行）
  - 区 C = test-reports/** + docs/（FIX-4/FIX-5、DOC 类 → 可与 A/B 并行）
  - 区 D = 只读（BW 盲行、GUI 测试）→ 永远可并行
- 冲突仲裁：git 索引由编排者独占（各执行者禁 git，收口时编排者按分区顺序合并 commit）
- FE-3 复测（区 D 只读）与 FIX 批（区 B/C）现在即可并行；FE-4 等 FE-3 复测过 + 修复闭环后启动
